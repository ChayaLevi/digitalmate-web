What they remember is `state.services` (`ServicesState`: group messages and how many fixture messages were posted, pizza orders, babysitter messages), seeded empty by `seedState` and so emptied by a demo reset. An older file without it reads as the seed (`servicesOf`). The pizza menu, babysitters, inbox and weather are fixed fixtures with dates from the demo clock.

Every adapter also accepts `title` and `summary` (what the card shows) and refuses any other unknown field. An adapter replaces `rt.state` without saving; `executeAction` saves right after it (with the card's outcome), and `actions.changed` re-reads every screen.
- T7.2: **the seeded Friday pizza rule** now carries the shop's ids and price: `{vendor: 'sim-pizza', items: [{id: 'margherita-l', qty: 2}], total: 178, currency: 'CNY'}` (the old `name` form would be refused). T7.3 can change the size from it (`quotePizza` prices any order).

- T7.2: **`POST /demo/post-group-message {}`** (demo only, signed in, any member): posts the next fixture message at the demo clock's now, saves, broadcasts the new stream message **`services.changed`** (no data; screens re-read) and queues **`homemind.message_received`** to PPMA (`groupMessageReport` in `ppmaMap.ts`; the group is family-wide). Answer `{ok, message, remaining}`; `409 no_more_messages` after the last one.

The demo button "Post next group message (demo) (n)" shows only with `HOMEMIND_DEMO=1` and while messages are left. The **inbox is the signed-in member's own mailbox**, approved senders only (Mom: class photo, library; Dad: class photo, swim club; Maya: none). Everyone with an account sees the tab.

- T7.1: **adapters** (`ActionAdapter` in `actions.ts`): `id`, `mode: 'real' | 'simulated'`, `area` (for `autonomy.byArea`), `autoAllowed?` (simulated only; ignored for real), `validate(payload)` and `execute(payload, signal)`. The bridge keeps a registry (`adapters` in `server/homemind.ts`), **empty for now**; T7.2 registers the simulated services there. `setHomemindAdaptersForTests` swaps it in tests.
- T7.1: **preparing a card** (`prepareCard`): `mode` and `area` are copied from the adapter, never from the caller, and `payloadHash` is sha256 of the canonical JSON (keys sorted). The adapter's `validate` must pass, the expiry must be in the future, at most 200 cards. Nothing runs. T7.3/T7.4 call this (then `commitCards`-style save and the `actions.changed` broadcast).
- T7.1: **the confirmation token** (`issueConfirmation`): `<base64url body>.<HMAC>`, body `{t: random id, c: card, h: payload hash, m: parent, exp}`, lifetime 15 minutes and never past the card's expiry. The key is derived from `HOMEMIND_SECRET` with its own label, so a session token never passes as one (tested). Issued only to a parent with an account for a pending card. Times are the **demo clock**, like card expiry. **Delivery:** `GET /screen/:name` adds `confirmations: {cardId: {token, expiresAt}}` for a parent when any card is pending (absent for others and when none). T7.3/T7.4's card buttons must send `{token}` from there; a card re-prepared with a new payload needs a new token (the screen re-reads on `actions.changed`).
- T7.1: **the guard** (`authorize`, pure). Tap: parent, token present, signature, same card, same member, not spent, card pending and not expired, token not expired, token hash = card hash, then the current payload hash = card hash, and the adapter's `validate`. Auto: refuse a real adapter (also when the card claims `simulated` but the adapter is real), an adapter without `autoAllowed`, a paused family, or an area level below 4. **A simulated adapter also needs a token on a tap**, so the flow is the same for every card.
- T7.1: **running** (`executeAction` with a `StateRef`): the token is spent and the card set to `executing` and saved **before** the adapter is called, so a double tap is refused (`not_pending`) and a failed run keeps the token spent. Adapter timeout 10 s (`AbortSignal.timeout`); a throw or timeout makes the card `failed` with a neutral error (the adapter's own message is not shown for a throw). Every outcome (`executed`, `failed`, `cancelled`, `expired`) writes one Activity `kind: 'action'`, `ref` = card id, `note` = outcome, with the card's `whyId`; **no Undo**. Level-4 runs and expiry have actor `homemind`.
- T7.1: **routes.** `POST /actions/:id/confirm {token}`: 200 `{card, activityId}`; refusals `400 no_token`, `403 not_parent | wrong_member | bad_token | wrong_card`, `404 not_found`, `409 not_pending | expired | token_expired | token_used | payload_changed | no_adapter`, `422 invalid_payload`, `502 action_failed` (with the failed card). A 409 carries the card as it is now ("This changed. Here is the latest"). `POST /actions/:id/cancel {}`: parents only. Both broadcast the new stream message `actions.changed` (no data; screens re-read).
- T7.1: **expiry** runs at the start of every scheduler tick (and so on a demo clock jump): pending cards past `expiresAt` become `expired`, logged, and `actions.changed` is broadcast.

- T6.2: **proposals** (`proposeFromPpma` in `ppmaMap.ts`, pure). The three tools only ever create a `proposed` item with `source {kind: 'ppma', label: 'PPMA'}`; `propose_item` is a task, or a 60-minute event when it has a `start`; `propose_preparation` goes under an **open or proposed, family-wide** event (a Parents-only or unknown event answers "No such event on the family board", so PPMA never learns it exists); `add_to_shopping` is a task whose note says nothing is bought. Arguments are checked by hand (title 1 to 120 characters, dates with an offset from 2 days back to 400 ahead, unknown arguments ignored): PPMA **cannot** set an owner, people, visibility, sensitivity or status. The outcome is `executed` (`path: auto`, result `{item_id, status: 'proposed', awaits}`); refusals are `rejected` with a plain `detail`: paused, bad arguments, already there (same words, type, time and event), **20 PPMA suggestions already waiting** (`PROPOSAL_LIMITS.waiting`), or a **hard preference** rules it out (`blockedChange`, the same check as the board's, with the word found).
- T6.2: **who the proposal "is by".** The core needs a member, so the technical actor is the first parent with an account, but the commit passes **no actor** (`commit(rt, state, events)`): no change alert "from" a parent, and the report back to PPMA names nobody. The item's `createdBy` is that parent (core limit); everything a screen says about origin comes from `source` and the Why. Proposed items show in everyone's Family list, like any proposed item; there is no push alert for them yet.
- T6.2: **the Why of a proposal** (`why-<itemId>`, `source: 'ppma'`): `summary` = PPMA's rationale (or "PPMA suggested this from what it knows about the family."), `decisionId` only if it is a well-formed id, basis `ppma_rationale`, `confidence`, and one `preference` entry per saved preference that applied **at that moment** (so after a preference is removed, the next proposal's Why no longer lists it).
- T6.2: **memory is read in the background.** `ppma.memory()` answers from a cache (`loading` before the first read, never a wait); `refreshMemory()` starts a read with the **owner** token (views list, then each view, at most 8 views and 200 statements each; one read per 5 s unless forced; a failed read keeps the last good list and sets `error`); a change that matters is announced once (`onMemory`) and the bridge broadcasts the stream message `memory.changed` (open Memory and item screens re-read). Announcing only on a real change means a screen cannot start a read loop. Statements whose text is just an event type (the fake profile's noise) are hidden; texts are trimmed of control characters and shown as plain text.
- T6.2: **PPMA's own signal.** The real PPMA sends `ppma.memory_updated` on the stream when its memory changes. The client then reads again after 0.8 s (a burst makes one read), **only if someone has opened the memory before**. After a correction it also reads once after 1.5 s and once after 25 s, as a fallback (a real model can take longer).
- T6.2: **corrections.** `POST /memory/correct {statementId, action: 'wrong' | 'forget'}`, **parents only** (`403` otherwise), `409 ppma_off` without PPMA, `404` unless the id is a statement PPMA showed us and says is `editable`, `409` if one is already on its way. It queues a `user.correction` (`{text: the statement's own text, statement_id, action}`) like every report, so **PPMA being down never blocks it**: the screen marks the statement "Correction sent. Waiting for PPMA to apply it." until a later read no longer has it (or 5 minutes pass). It writes no Activity and has no Undo (a statement PPMA forgot is not Homemind's to restore). There is no free-text "replace" yet: "That's wrong" and "Forget" are PPMA's `wrong` and `forget`.
- T6.2: **who sees what.** Every member with an account sees the Memory tab; only a parent gets the buttons (a teen is told so). Only family-wide data ever reaches PPMA, so its memory holds nothing Parents-only. **Homemind's saved preferences** are on the same screen as a second list ("Saved by Homemind") with **Remove** (a parent for any, anyone for a soft one; the server decides, hard ones need a parent as before). Removing one reports `preference_stated` (removed) to PPMA, which is the "corrected in both places" the plan allows. There is **no automatic link** between a PPMA statement and a saved preference (PPMA statements carry no source id, so matching by words would be a guess).
- T6.2: **"Why?"** `GET /why/:id` adds `ppma: {state: ready | loading | unavailable, summary?, rationale?, basis?}` for a PPMA Why; the item screen shows "Why is this suggested?" (PPMA's reason, saved preferences considered, PPMA's explanation, source) and the chat Why card and the tap-"Why?" notice add the same. The explanation is fetched in the background with the owner token and cached (100 entries; an `unavailable` answer is retried after 30 s); the first ask answers `loading` and `memory.changed` brings the rest. **A PPMA Why with no decision id says so** ("PPMA gave no decision record") and shows Homemind's own record, never PPMA's voice. A rule's or the model's Why is unchanged and never labelled PPMA.
- T6.2: **the Memory tab** is new in the sub-navigation (`Memory` / `记忆`, after Rules); the plan lists Memory there, T3.2 had left it out because the screen was 501.

- T6.1: **when PPMA is on.** Only with `PPMA_URL` set (no default URL in the code). The owner token comes from `PPMA_OWNER_TOKEN`, else `PPMA_OWNER_TOKEN_FILE`, else PPMA's own `~/.config/ppma/setup-token`. `PPMA_SPACE` defaults to `me`; `PPMA_TIMEOUT_MS` (default 10 s) is the per-call timeout. The owner token is used only for the manifest and the token mint; the **app token lives in memory only** and is minted again at start and after any 401. Neither token is logged or saved.
- T6.1: **the client** (`server/homemind/ppma.ts`) is one per runtime (`rt.ppma`), started when the state loads and stopped by `resetHomemindRuntime()`. Two loops: the **outgoing queue** (`emit()` only pushes and returns at once; batches of up to 100 to `POST /messages`; 202 removes them; 401 re-mints; 422/400 drops the ids PPMA names, else the batch, with a log line, so one bad message never blocks the rest; anything else backs off 1, 2, 4, 8, 15, 30 s) and the **stream** (one long-lived `GET /stream?app=homemind` with `Last-Event-ID`; silence over 45 s counts as dead, PPMA's heartbeat is 15 s; a 401 also forgets the stream position and reads from the start, because a restarted fake PPMA forgets its ledger too, and commands are de-duplicated anyway). Status: `off`, `connecting`, `ok` (stream open and the last call worked), `offline`; `info()` adds `queued` and a short `lastError` code.
- T6.1: **saved sync state** in `<state file>.ppma.json` (`.homemind/state.ppma.json`, e2e `.homemind/e2e-state.ppma.json`): the outbox (at most 1000; the oldest reports go first, never an outcome), `lastStreamId`, and the last 2000 handled command ids. It is beside the state file, not in it, so **a demo reset does not make old commands run again**. A command's outcome and its handled id are saved in the same write.
- T6.1: **commands.** Every command gets exactly one `command.outcome` with `causation_id` = the command id (and its `correlation_id`). A repeat delivery is skipped. Past `expires_at` (real time): `expired`, the handler is not called. A throwing handler: `failed`. `dismissed` is always `path: asked`. The handler is `handlePpmaCommand` in `server/homemind/ppmaMap.ts` (pure): `homemind.get_board` → `executed` with the family-wide board (open and proposed items from 2 days back to 45 days ahead plus undated and weekly ones, at most 60, members, time zone); `propose_item`, `propose_preparation`, `add_to_shopping` → `rejected` "Homemind does not take proposals from PPMA yet" (**T6.2 replaces this**; the handler may return a new state, which the bridge commits); `ui.*`, `policy.set_threshold` and anything else → `rejected` with a reason.
- T6.1: **the manifest** is `HOMEMIND_MANIFEST` in `ppma.ts` (the old `scripts/ppma-homemind-manifest.json` stays for the smoke script). Same events and tools as T0.2, with real input schemas and `x-ppma-carries`, and **`ui_commands: []`**, so PPMA sends Homemind no `ui.notify`/`ui.ask` (Homemind does not show them). No tool with effect `send` or `external`.
- T6.1: **what is reported** (`reportsForChange`, `preferenceReport`, `reminderReport`): `homemind.item_changed` for every item a change touched that is family-wide before or after (`change`: `created`, `changed`, `removed`, or `hidden` when it became Parents-only, with nothing but the id); fields: id, type, title (EN, ZH), notes (500 chars), start, end, all day, weekly days, status, importance, ownership, owner id and name, confirmed, candidates, for whom, away, parent event, source kind, version, actor id and name. A **sensitive** item goes without title and notes. `homemind.member_unavailable` once per away member when a family-wide event newly makes them away (not on a notes edit). `homemind.preference_stated` on every saved preference change (reason, scope, strength; a removal carries no text). `homemind.reminder_outcome` for "Got it" / "Remind me later" on family-wide items. **Parents-only items, and preparations under them, are never sent.** `homemind.message_received` is declared but not sent yet (T7.2/T7.4). `occurred_at` is real time; item times are absolute.
- T6.1: **health** gives `ppma` (`off`/`connecting`/`ok`/`offline`) and `ppmaQueued`. Screens get `ppma` in the JSON and pass `off`/`offline`/`ok` to the surfaces (`connecting` counts as offline). `hello` carries `ppma`, and a new stream message `ppma.status {status}` goes to every stream on a change. The Family tab shows a **PPMA offline** / **PPMA 离线** chip next to Live only while offline (nothing when off or ok).
- T6.1: **e2e runs with PPMA set up but unreachable** (`PPMA_URL=http://127.0.0.1:9` on the 5176 server), so every Homemind e2e test also shows the board working with PPMA down.

- T5.4: **saving.** `POST /preferences`: `{text, reason?, aboutMemberId?, strength, scope?}` saves; with `id` it corrects that one; `{id, remove: true}` removes; `{undo: activityId}` undoes. A save with no `id` whose words match a saved one (same person and scope, case and punctuation aside, or the seeded Chinese text) corrects it instead of adding a twin. Anyone with an account may add one (a teen too); **only a parent may correct or remove a hard one, or switch hard and soft**. Scope is stored lowercased. At most 200 preferences, text and reason 500 characters each. Every change writes one activity `kind: 'preference'` (`ref` = the preference, `note` = `added`/`corrected`/`removed`/`undone`) carrying `prefUndo: {preferenceId, before}`; Undo is allowed to the member who made it or a parent, once, and only for the latest change to that preference. Streams get `preferences.changed` (screens re-read). Seeded Chinese text is kept when the English words still match; a seeded Chinese reason is dropped when the reason changes.
- T5.4: **chat.** `add_preference` at level 2 and up, not paused: saved at once, the card shows what was saved (preference, about, because, applies to, strength) and Undo, and asks the member to check the reason is theirs. **Level 1 or paused: nothing saved**, the card has a Save button (it calls `POST /preferences`, run on the Family tab like every chat-card button). The prompt now tells the model: `text` without the reason, `reason` copied from the member's own words (never from the board), scope as short English words joined by `-`. The fake model drops the "because …" part from `text`.
- T5.4: **where a preference applies** (`appliesTo`, pure). About a member: items for that member; a **scoped** one also items for nobody in particular (a party read from a group) when the scope matches; unscoped ones only where the member is named. A scope matches when every concept it names is in the item's words, in English or Chinese (`kindergarten` = kindergarten/preschool/幼儿园/..., `party` = party/派对/聚会/..., and about 10 more), plus any other word literally. The words: the item's title in both languages, notes, its parent event's, the source label, and `tags` a caller passes (T7.4: the kindergarten group passes `kindergarten`, since the 接龙 party, 秋季水果派对, does not say 幼儿园). A preparation for nobody is for its event's people, or the whole family when the event names nobody.
- T5.4: **the hard block.** A hard preference's text (both languages) gives what it rules out (`No X`, `allergic to X`, `X-free`, `X allergy`, `不吃X`, `对X过敏`, ...), with words for about 12 common allergens and dietary rules in both languages. ## Demo facts to say out loud

Things that are simulated or limited, kept current for the presenter.

- The demo is the web version, not a native HarmonyOS app.
- The group, vendor, babysitter, inbox and weather are simulated and labeled. They are on the **Services** tab, with a "Simulated / 模拟" badge on every row. The kindergarten group gets its messages from a demo button ("Post next group message"), not from WeChat. The pizza shop, the babysitters' answers and the inbox are fixed sample data; nothing is ordered, sent or read from a real mailbox.
- Real WeChat group access is not available. The realistic product route is sharing and screenshots.
- The 接龙 screenshot used in tests is simulated and says so. Extraction was measured only on that one clean image, not on real photos.
- PPMA's memory and proposals need the live model and network on stage (replay does not work). Without them the board still works, and the Family tab shows "PPMA offline". What Homemind reports waits in a queue and is sent when PPMA is back. Parents-only items are never sent to PPMA.
- PPMA's own notifications (`ui.notify`, `ui.ask`) are not shown in Homemind; the manifest asks PPMA not to send them.
- Reminders and escalation are banners inside the open app (Family tab). There are no push notifications, so a phone in a pocket gets nothing.
- The backup contact (Grandma Lin) is simulated: nothing is sent. The banner says "(Simulated)". Settings can rename or remove it, and it stays simulated.
- Settings are per family on one demo server. The demo sign-in is not authentication, so "parents only" for family settings protects against a teen's window, not against someone picking "Mom" in the picker.
- The demo clock moves only the app's own time, and only forward. A reset puts it back.
- Chat with the Family companion reads **one message at a time**: it has no memory of the earlier messages in the conversation. It can answer, add, assign, take, mark done, explain and save preferences. Rules and "someone is sick" from chat say "not built yet" until T7.3, T8.1.
- A **hard** preference (allergy, dietary law) blocks a preparation or task that names the thing it rules out, from chat or the board. It works by simple patterns and a short word list in both languages (peanut, nuts, kiwi, egg, dairy, pork, gluten, shellfish, fish, sesame, soy, meat), not by understanding food: "satay" would pass. Say "it helps, but it can miss things" (never call it a safety feature).
- "Family preferences that apply" on an item: matched by words in the title (for example "kindergarten" + "party"), not by meaning.
- A screenshot sent in chat becomes **suggestions** (proposed items) only; a person taps Approve. The model reads it (live Flash about 2 to 3 s per screenshot); the quotes are shown so people can check. Tested on 3 clean rendered screenshots and 2 texts (all simulated samples), not on real phone photos. The 接龙 sign-up is shown, not claimed (claiming is T7.4).
- "Why?" in chat is Homemind's own board record (who added it, how, who has it, the last change) and says it is not from PPMA. For an item PPMA suggested, "Why?" (chat card, item screen) shows PPMA's own reason, the saved preferences Homemind weighed, and PPMA's explanation **only if PPMA has one for that decision**; if it has none, the screen says so.
- The **Memory** tab shows two lists, labelled: what PPMA remembers (PPMA's words, with a confidence; needs PPMA and the network; parents can say "That's wrong" or "Forget") and what Homemind itself saved (preferences, with Remove). Without PPMA only the second list shows, with a "PPMA offline" notice. A correction to PPMA is sent and shown as "waiting" until PPMA has applied it, which can take seconds with the live model.
- PPMA can only **propose**: a task, an event or a preparation lands as "Proposed" with a reason, and a parent taps Approve. It cannot assign, buy or send. At most 20 of its suggestions wait at once.
- With `HOMEMIND_LLM=fake` the chat "model" is canned keyword rules, labelled "Simulated model". The live model (DeepSeek Flash) needs network on stage: about 1 to 1.7 s per chat message, about 3 s per screenshot.
- **Every action needs its own tap, in code.** A rule only prepares a card; running it needs a parent's tap on that card, with a single-use confirmation bound to that card, that parent and the exact contents. If the contents change, the old tap is refused. Autonomy level 4 may act alone only against simulated services. The demo has **no real adapters** (nothing can buy, pay or send), so the "real" path is proven by unit tests only.
- On Huawei phones, DigitalMate's chat runs through the Orbit server. Homemind's logic is kept separate so it can move there later.
